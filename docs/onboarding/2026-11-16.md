## Boundary and method

A fresh Linux Docker-in-Docker environment received only `git archive` of the committed source. It had its own daemon, no images/containers/volumes, a new non-root user (UID/GID 10001), empty npm cache, and no application, home, Docker authentication or Siftable configuration from the host. No host home/socket was mounted and no host ports were published. The harness provides the documented prerequisites: Node/npm and Docker access. Network downloads fetched public dependencies/images. Normal setup did not need a global Sift CLI, old monorepo, private helper, populated `.env`, model credential or hosted account.

The test is `npm run test:readme`. It always tests committed HEAD. The [runner](../../scripts/readme-check.mjs) packages the source, and the [verifier](../../scripts/cleanroom/verify.mjs) executes documented operations and checks their effects. The [first-work example](../../scripts/first-work.mjs) is included in the repository and linked directly from the README; it uses real CLI processes and the MCP SDK's stdio client, with no direct database/service implementation calls. This is an executable tutorial, not a delegated model agent.

Runtime: Node 22.23.3, Linux arm64, Docker 29.9.3, Compose 5.7.1, PostgreSQL 17. The harness uses privileged Docker-in-Docker to isolate configuration and state; this is not a security sandbox or proof of all host-platform behavior.

## Failure and repairs

The original README's `npm ci`, build and startup succeeded in the baseline. However, startup reported ready while the first CLI catalog call failed with `EACCES`: `.local` belonged to user 1000, but Docker bootstrap wrote `owner.json` as root with mode 0600. The original file permissions, failure and source revision are retained. This disproved startup readiness as an onboarding success criterion.

Compose administration now derives UID/GID from its mounted private directory and drops root before issuing credentials or writing backups. No permission broadening or fixed UID is used. The final fresh run verified user 10001 owned its mode-0600 credential and mode-0700 backup directory. A temporary ownership correction was used only to investigate the baseline further; it was not used in the final fresh run.

The README also depended on finding an owner UUID in earlier bootstrap output and assembling the first useful work cycle from separate contracts. `config.info` now exposes an explicit identity-only whitelist without the token. The README's runnable example supplies the full CLI/MCP journey, and explains prerequisites, port configuration, one-installation-per-daemon scope, safe troubleshooting and restart readiness. A new test verifies identity output and refusal of a broadly readable credential file.

During example development, its expected error wording differed from the actual refusal (`Credential does not authorize this operation`). The server correctly denied the action; the assertion was corrected before the fresh run. No authorization behavior was relaxed.

## Observed results

- Freshness assertions passed before installation, including zero daemon images/containers/volumes and no npm/application/configuration state.
- A CLI call without configuration failed before bootstrap. Default `npm ci`, build and `npm run local` then succeeded without manual repair, and the CLI inspected all six modules and schemas.
- CLI created a project, source note and work item. Identical request-key replay returned the same work ID. CLI claimed using a scoped temporary agent credential.
- A real stdio MCP session started that CLI-held claim, read and compared the exact source note, built a revision-bound context packet, submitted passing evidence and requested review. Both MCP and direct CLI refused agent acceptance.
- The owner CLI recorded scripted acceptance: `done`, `commands_passed`. This is test/operator acceptance, not Thomas's or an outside human's acceptance. The temporary credential was revoked.
- The README stop/start commands retained accepted work. Backup verification and restore checked 23 tables, and the documented service switch exposed the same accepted work and source note through the recovered API.
- All 10 unit/CLI tests and all 15 packaged integration scenarios passed (16 Node tests including the parent), with zero failures or skips. Build/type checking, formatting and whitespace checks passed. Broader regression includes modularity, CRUD, lease recovery and migration negative controls.

All owned cleanroom containers and anonymous volumes were removed. Logs/source hashes/receipts remain, but disposable test credentials and databases do not. The existing real pilot's container ID, image ID and start time matched before/after and its health check passed. Its data was not mutated. The locally tagged application image was updated for future admin commands, and its new admin entrypoint was checked on the Mac with the read-only module planner; the existing server process was not restarted.

## Remaining gate

This closes the reproducible automated clean-environment setup gate for this Linux/Node/Docker combination. Independent human comprehension, another physical host/architecture, installation of Docker itself, performance, and independent security/recovery review remain unproven. The next useful test is a fresh operator following this README without live hints, alongside independent review of credential scopes, migrations and recovery. Optional domain expansion and public release remain deferred.
