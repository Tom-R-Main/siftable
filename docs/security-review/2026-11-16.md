## Findings and resolution

| Finding | Baseline evidence | Correction | Required effect checked |
|---|---|---|---|
| P2: replaying claim A overwrote later claim B's private lease | Actual CLI A claim/release, B claim, A retry made B's start fail with stale lease | Private immutable claim candidates; a current-principal-only `work.lease` resolver; immutable per-mutation request bindings | Historical and delayed claim responses cannot replace custody; write-only agents resolve only their own lease; old mutation retries still reach receipts after release; same-URL restoration accepts lower/reused epochs |
| P2: installing Planning while Projects was disabled bypassed the dependency invariant | Admin install succeeded when rejection was required | Installation takes the API's module-state lock and validates enabled prerequisites before transaction commit | Rejection preserves the disabled state and leaves no Planning schema; reenable/install/task creation succeeds; concurrent install/disable cannot commit an invalid state |
| P2: failed restore could falsely claim quarantine after a lost database response | A committed CREATE retained unrestricted default connectivity; a committed final GRANT remained usable after the injected response loss | Target starts with a zero ordinary-connection limit; final access changes commit together; failure reconciles access and sessions before claiming quarantine, otherwise reports uncertainty | Actual new runtime connections refused; an already-open runtime session terminated; unavailable reconciliation explicitly reports unknown; a lost CREATE response does not trigger cleanup against an uncertain target |

Observed during repair: the credential reviewer found a compatibility regression in the first candidate fix. Pre-upgrade release receipts had no new mutation-binding file, so the resolver rejected their replay after the lease ended. Root reproduced that through the packaged CLI, retained the failure, and added a bounded legacy fallback. It tries the original secret/epoch without saving a guess, and only a definite stale-lease response permits fresh resolution. The final legacy-format test replays the released receipt, replays its old claim receipt, then adopts a new claim successfully.

Observed probe defects were also retained: an early positive-control assertion expected the create response's project field in get-response spelling; it was replaced with an actual `tasks.get` readback. A restore test initially reused its own source database name; the product correctly refused it, and the probe now uses a distinct target. Neither was counted as a product finding or repaired by weakening product behavior.

No baseline SQL migration changed, and no data/schema migration is required for these fixes. The registry now has 61 operations, including the narrowly authorized lease resolver. Clients and server must use the same build. Client lease retry bindings are endpoint-specific; moving to a different API URL requires fresh claim/request keys. The documented same-URL recovery procedure preserves custody. Server receipts themselves remain unchanged.

Restore now explicitly requires a PostgreSQL superuser, matching the local Compose administrator; the serving role remains restricted. The [PostgreSQL 17 CREATE DATABASE contract](https://www.postgresql.org/docs/17/sql-createdatabase.html) documents that connection limits do not restrict superusers. Root verified ordinary-connection denial against PostgreSQL, rather than relying only on that documentation. A failed cleanup can still leave access unknown when the server is unreachable; the tool reports this instead of claiming safety it cannot observe.

## Additional clean-environment run: infrastructure failure

Observed: the committed-head clean run bootstrapped successfully and completed the real CLI/MCP tutorial. During its documented stop/start, Docker reported an I/O error updating its networking store. Cleanup then failed because Docker Desktop's metadata filesystem was read-only. The [failure transcript](readme-storage-failure.txt) preserves both effects. This is not a passing clean-environment recovery rerun, despite the separate packaged recovery suite passing before the storage failure.

Observed afterward: the existing pilot's container ID, image and start time still matched the pre-review values, but its health endpoint returned HTTP 500. Host free space was 14 GiB at the observation. The root cause of the Docker filesystem error is unavailable; disk pressure is not asserted as its cause. At that point, no broad pruning, volume deletion, service restart or machine repair had been attempted. The run-owned helper `sift-readme-71dbb012` could not be removed reliably because Docker's metadata store rejected writes.

Thomas then approved: ‘Restart Docker and finish verification.’ Root ran `docker desktop restart --timeout 120`, removed only the failed review helper and its disposable volume/image, and resumed the existing pilot containers with `docker compose start`. The pilot retained its container ID and application image and returned HTTP 200. No application data or private credential values were read or changed.

## Limits and next decision

Unavailable: independent human onboarding, broader physical-host/architecture coverage, load/performance qualification, adversarial code execution as the trusted database administrator, and a comprehensive penetration test. Existing-role/RLS configuration validation is not a claim to repair deliberate administrator changes. Post-snapshot credential revocations must be reapplied against the recovered database before serving it; recovery cannot infer later security decisions.

Recommendation: keep optional domains and publication deferred now that the scoped review and complete clean-environment rerun pass. The next learning gate is an independent operator completing a bounded project and recovery using the README without live hints. Local review and tests support that trial; they do not authorize a release or prove recurring adoption.
